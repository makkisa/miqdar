# مِقدار

تطبيق React + TypeScript + Vite لتتبع الطعام والسعرات والماكروز. لا توجد بيانات تجريبية في التطبيق. افتح `STATUS.md` لمعرفة ما تم اختباره وما يحتاج إعدادًا أو استكمالًا.

## تشغيل Windows

ثبّت Node.js 22.12 أو أحدث (نسخة LTS)، ثم افتح PowerShell داخل هذا المجلد:

```powershell
npm ci
Copy-Item .env.example .env.local
npm run dev
```

افتح العنوان الذي يطبعه Vite. تسجيل الدخول إلزامي؛ اضبط Firebase في `.env.local` للتطوير. إذا لم تهيئه تظهر شاشة دخول غير مفعلة، ولا يمكن تصفح التطبيق. للبناء:

```powershell
npm test
npm run build
npx vite preview --host 127.0.0.1
```

لتشغيل API في نافذة PowerShell ثانية بعد ضبط متغيراته:

```powershell
node --env-file=.env.local --import tsx server/index.ts
```

الخادم يتصل افتراضيًا بـ127.0.0.1:8787، وVite يمرر `/api` إليه. في الاستضافة ضع reverse proxy HTTPS أمامه أو اضبط `VITE_API_BASE` إلى أصل الخادم مع `ALLOWED_ORIGIN` مطابق تمامًا لأصل الواجهة. لا تنشر ملف حساب الخدمة أو `.env.local`.

## Firebase وGoogle

المشروع المرتبط بهذه النسخة هو `miqdar-de610` على Spark. أُنشئت قاعدة Firestore في `me-central1`، ونُشرت القواعد، وفُعّل Google، وأُضيف نطاق الموقع المنشور إلى Authorized domains. يحتوي `.env.production` على إعدادات الويب العامة للبناء الإنتاجي. لا تضع مفاتيح Gemini أو Admin في هذا الملف. الخطوات التالية لإعادة إنشاء الربط في مشروع آخر:

1. أنشئ مشروع Firebase، واختر Spark إن كان يلائم حصتك. أضف Web App وCloud Firestore في وضع الإنتاج.
2. فعّل Authentication → Google، وحدد بريد الدعم. أضف نطاق الموقع وlocalhost إلى Authorized domains عند الحاجة.
3. انسخ قيم إعداد تطبيق الويب إلى متغيرات `VITE_FIREBASE_*`. هذه معرفات عامة وليست مفتاح Gemini أو اعتماد Admin؛ الأمان يأتي من القواعد.
4. انشر `firestore.rules` باستخدام Firebase CLI. لا تستخدم قواعد test mode.
5. تستخدم النسخة نافذة Google popup عندما يختلف نطاق الموقع عن `authDomain` لتجنب التخزين المحظور عبر المواقع في Safari. يبدأ فتح النافذة مباشرة عند الضغط. يستخدم redirect على iPhone فقط عند تطابق النطاقين. لا تفعل redirect عبر نطاق خارجي دون إعداد proxy مناسب لمسار `/__/auth/` وفق الوثائق. مجرد إضافة النطاق للقائمة لا يحل منع التخزين عبر المواقع.
6. أعد البناء بعد تغيير متغيرات Vite. اختبر تسجيل الدخول والعودة من Safari ومن تطبيق الشاشة الرئيسية كلًا على حدة.

بناء GitHub Pages يقرأ إعداد Firebase العام من Repository Variables باسم `VITE_FIREBASE_API_KEY` و`VITE_FIREBASE_AUTH_DOMAIN` و`VITE_FIREBASE_PROJECT_ID` و`VITE_FIREBASE_APP_ID`. يقرأ `VITE_API_BASE` رابط خادم الصور إن كان منشورًا. لا تضف Gemini API Key إلى متغيرات Vite.

المراجع: [Firebase redirect](https://firebase.google.com/docs/auth/web/redirect-best-practices)، [التخزين دون اتصال](https://firebase.google.com/docs/firestore/manage-data/enable-offline).

## التخزين والمزامنة

للحساب المسجّل: Firestore هو مصدر البيانات الوحيد، مع IndexedDB persistence المدمج. listeners تعرض الكتابات المحلية فورًا؛ SDK يحتفظ بطابور الكتابات ويعيد إرسالها. `setDoc` يستخدم معرف السجل نفسه عند التعديل أو إعادة إرسال نفس العملية؛ إعادة إضافة طعام مقصودة تنشئ سجلًا جديدًا. لا يوجد طابور مخصص موازٍ.

لا يوجد دخول ضيف في الواجهة. لا تُقرأ السجلات قبل التحقق من جلسة Firebase، وعند تسجيل الخروج تُحجب صفحات التطبيق. بيانات الضيف القديمة لا تُحذف ولا تُنقل تلقائيًا لأي حساب. الاستيراد يتجاهل المعرفات الموجودة، حتى المحذوفة، لمنع إعادة السجلات أو إحيائها من نسخة قديمة.

تعارض تعديل السجل نفسه: آخر كتابة تصل للخادم تفوز حسب Firestore، وليس ساعة الجهاز. الحذف tombstone (`deleted=true`) ويفوز وفق السياسة نفسها؛ تعديل متأخر من جهاز دون اتصال قد يعيد السجل. هذا اختيار واضح وليس حلًا يعطي أولوية مطلقة للحذف. لا نحذف tombstones تلقائيًا.

تسجيل الخروج العادي يتطلب اتصالًا ومزامنة الكتابات، ثم إنهاء Firestore ومسح cache الحساب قبل الخروج. انتهاء الجلسة لا يمسح الطابور؛ أعد تسجيل الدخول بالحساب نفسه لإكماله. لا يُظهر التطبيق بيانات UID آخر. التخزين على الجهاز غير مشفّر على مستوى التطبيق؛ استخدم جهازًا موثوقًا. فتح عدة تبويبات غير مدعوم بقصد: مدير persistence أحادي التبويب يفضّل خطأ ظاهرًا على طبقتي تخزين متنافستين. إغلاق التبويب الآخر يعالج التعارض.

أهداف التغذية وتفضيل اللغة محفوظة محليًا؛ الأهداف مفصولة حسب UID لكنها غير متزامنة عبر الأجهزة في هذه النسخة.

## Gemini API آمن

تستخدم النسخة المنشورة وسيطًا اختياريًا على **Cloudflare Workers Free** بدل Firebase Functions، لذلك لا تتطلب ترقية Firebase أو تفعيل فوترة. ملف `worker/index.ts` يتحقق من Firebase ID token، يفرض أصل GitHub Pages، يحد حجم الإدخال، ويفرض حدًا تقريبيًا لكل مستخدم عبر Rate Limiting. يبقى المفتاح Secret داخل Worker؛ لا يوضع في Vite ولا في ملفات المستودع. حد Workers المجاني المنشور حاليًا 100,000 طلب يوميًا، وقد تتوقف الطلبات عند بلوغ الحد. حدود Gemini المجانية منفصلة وقابلة للتغيير.

للنشر مرة واحدة: أنشئ حساب Cloudflare مجانيًا وفعّل workers.dev، ثم أضف GitHub Actions Secret باسم `CLOUDFLARE_API_TOKEN` بصلاحية Workers Scripts Edit، وRepository Variable باسم `CLOUDFLARE_ACCOUNT_ID`. الـworkflow ينقل `GEMINI_API_KEY` المحفوظ كـGitHub Secret إلى Worker Secret، ينشره، ويضبط `VITE_API_BASE` تلقائيًا ثم يعيد بناء GitHub Pages. بعد الإعداد يمكن تحديث كود Worker عبر GitHub Actions دون نشر المفتاح للواجهة. لا ترسل رمز API Token أو Gemini في المحادثة.

اضبط على الخادم فقط:

- `GEMINI_API_KEY`: مفتاح Google AI Studio.
- `GEMINI_MODEL`: اسم نموذج متاح في حسابك يدعم الصور وStructured Outputs. لا يُختار نموذج مدفوع تلقائيًا.
- `GOOGLE_APPLICATION_CREDENTIALS`: مسار حساب خدمة Firebase Admin خارج المستودع، أو استخدم هوية البيئة المُدارة.
- `ALLOWED_ORIGIN`: أصل الواجهة HTTPS.
- `REQUIRE_APP_CHECK=true` بعد إعداد App Check ومراقبته.

خادم Express السابق يطبق 20 طلبًا يوميًا لكل UID. Worker يطبق حدًا تقريبيًا 20 وحدة لكل دقيقة لكل UID (الصورة تستهلك 4 وحدات)؛ حدود Cloudflare مستقلة لكل موقع تقريبية وليست سقفًا عالميًا صارمًا. الاستجابة تفحص بـZod على الخادم والعميل. لا يكتب النموذج في بيانات الطعام؛ التطبيق يعرض أزرار تأكيد ومراجعة. لا توجد سجلات للصور في التطبيق أو الخادم. تظل الصورة في الذاكرة أثناء الطلب، وتزال من حالة المرفق بعد نجاحه.

الصور تُضغط محليًا إلى JPEG حتى 1600px. الإرسال لا يبدأ قبل موافقة المستخدم. الخطة المجانية قد تستخدم المدخلات لتحسين منتجات Google؛ لا ترسل صورًا حساسة. راجع [سياسة الأسعار والبيانات](https://ai.google.dev/gemini-api/docs/pricing) و[Structured Outputs](https://ai.google.dev/gemini-api/docs/structured-output) قبل اختيار النموذج؛ الحصص تختلف ولا يوجد وعد بخدمة مجانية غير محدودة.

استخراج الملصق يستخدم فهم الصور متعدد الوسائط في نموذج Gemini المحدد على الخادم وإخراج JSON وفق Schema؛ لا توجد خدمة OCR مستقلة. يقرأ القيم الظاهرة فقط ويترك غير الواضح `null`، ثم يفتح نموذج المنتج مباشرة معبأً بالسعرات والماكروز لمراجعتها وحفظها. إذا كانت الحصة أساس القيم ولا يُعرف وزنها، يطلب التطبيق تحديدها أولًا. لا يُرسل المفتاح إلى المتصفح.

App Check: سجّل Web App بمزوّد reCAPTCHA v3، ضع `VITE_APP_CHECK_SITE_KEY`، وراقب طلباتك قبل enforcement على Firestore. فعّل enforcement خادميًا للذكاء الاصطناعي بعد التحقق. App Check لا يستبدل Authentication أو Security Rules ولا يمنع كل عميل معدل.

حذف الحساب: endpoint يحذف مسار المستخدم تكراريًا وحصته، ثم يحذف العميل هوية Auth. يتطلب تسجيل دخول حديثًا (5 دقائق). إن ظهر خطأ أعد تسجيل الدخول ثم حاول. لا تُحذف نسخة الضيف أو النسخ التي صدّرها المستخدم خارج التطبيق.

## الباركود والدقة

الماسح يقرأ صيغًا متعددة من `BarcodeDetector` عند توفرها، وZXing محمل عند الطلب خلاف ذلك. تصوير مستمر، إدخال يدوي، وقراءة صورة محفوظة. توقف الكاميرا عند إغلاق الشاشة أو إخفاء التبويب؛ أعد فتح الماسح لاستئنافها. قاعدة الطعام تبحث بأرقام EAN/UPC وGTIN، بما فيها توسعة UPC-E الصحيحة؛ الرموز الأخرى قد تُقرأ لكنها لا تُعرّف منتجًا غذائيًا عبر Open Food Facts.

بحث الباركود يبدأ بالمطابقة الدقيقة في Open Food Facts ثم USDA FoodData Central، ولا يعتمد تخمين رقم غذائي من الباركود. البحث بالاسم يجمع المصدرين، يقدّم الأطعمة الأساسية الطازجة على المنتجات المركبة عند البحث باسم عام، ويستبعد النتائج البعيدة أو التي ينقصها أحد الماكروز. قيم USDA التجارية مطبّعة أصلًا لكل 100 g/ml في رد API؛ لا تُقسم على حجم الحصة مرة أخرى. لا تُسجّل أي نتيجة تلقائيًا؛ راجع الاسم والماكروز والمصدر أولًا. يستخدم البحث مفتاح USDA `DEMO_KEY` العام للاستخدام الفردي وقد يتأثر بحدود الخدمة؛ يمكن استخدام مفتاح data.gov خاص عبر وسيط خادمي إذا زاد الاستخدام. إذا لم تظهر بيانات موثوقة، صوّر الملصق الغذائي. راجع أساس g/ml على الملصق، خصوصًا المنتجات السائلة. بيانات OFF خاضعة لترخيص ODbL: [وثائق OFF](https://openfoodfacts.github.io/openfoodfacts-server/api/). بيانات USDA عامة المجال وفق [دليل API](https://fdc.nal.usda.gov/api-guide/).

تُعرض نتائج البحث مع القيم لكل 100 g/ml والمصدر؛ لا تُعرض نتيجة بحث ناقصة كأن الماكروز صفر. عند مسح باركود ببيانات ناقصة، أي بديل يظهر بوضوح كمنتج مشابه وليس مطابقًا، ولا يُسجّل دون مراجعة.

التحويلات حتمية: kg وoz إلى g، وL إلى ml. لا تحويل بين الكتلة والحجم دون كثافة. القطعة/الكوب/الملعقة تحتاج وزنًا أو حجمًا خاصًا لكل استخدام؛ لا يوجد جدول تحويل عالمي. يحتفظ المنتج بحجم حصة واحد، لذلك راجعه عند تغيير نوع الوحدة المنزلية. قراءة الملصق تحفظ النص المنظم الأصلي والقيم الموحدة. إذا غاب حجم الحصة فلا تحويل تلقائي.

## النشر والتكلفة

الواجهة الثابتة يمكن نشرها عبر Firebase Hosting على Spark ضمن حصتها باستخدام:

```powershell
npx firebase-tools login
npx firebase-tools use --add
npm run build
npx firebase-tools deploy --only hosting,firestore:rules
```

لا يرفع هذا خادم Node. OAuth أسهل عند استخدام نطاق Hosting نفسه كـauthDomain. Firebase Hosting يوفر HTTPS؛ افتح Safari ثم مشاركة → إضافة إلى الشاشة الرئيسية. بعد التحميل الأول، الصفحات والكتابات المحلية تعمل دون إنترنت. استجابات API والصور لا تدخل Workbox runtime cache. تحديث SW يطلب ضغط زر ولا يجري أثناء وجود كتابات معلقة.

يمكن تشغيل الخادم على جهازك للتطوير دون رسوم استضافة. للاستعمال خارج المنزل تحتاج استضافة Node HTTPS أو تكييفه مع Serverless. لم تُفعّل فوترة أو خدمة مدفوعة. Firebase Functions وCloud Run ليستا ضمانًا لاستضافة مجانية بلا فوترة؛ راجع [أسعار Firebase](https://firebase.google.com/pricing) أولًا. يمكن نشر الواجهة فقط والاستمرار باليدوي والباركود حتى اختيار استضافة API.

## الاختبارات

```powershell
npm test
npx playwright install chromium webkit
npm run test:e2e
npx firebase-tools emulators:exec --only firestore "npm test"
```

اختبارات القواعد تتخطى نفسها عند غياب `FIRESTORE_EMULATOR_HOST`. يتطلب Emulator Java متوافقًا مع Firebase CLI. اختبارات E2E تستخدم بيانات اختبار معزولة وليست بيانات مبدئية داخل التطبيق.

قبل الاستخدام الإنتاجي: اختبر iPhone حقيقي، أذونات الكاميرا، وضع standalone، إعادة فتح دون اتصال، الانتقال بين حسابين، انتهاء الجلسة، وكتابات جهازين متعارضة. WebKit المكتبي لا يعادل iPhone Safari.

## الأداء والهيكل

`src/domain.ts` للحسابات والمخططات، `store.ts` للتخزين، `firebase.ts` للهوية، `products.ts` للبحث في OFF وUSDA، `Scanner.tsx` للكاميرا، `AI.tsx` للذكاء الاصطناعي، و`server/index.ts` للخادم. لا حاجة إلى Query/Zustand مع Firestore listeners وحالة React المحلية في هذا الحجم.

Web Vitals تسجّل في console أثناء التطوير. علامات Performance: `camera-open`, `barcode-recognized`, `product-lookup`. تقارير Lighthouse تؤخذ من build الإنتاجي؛ لم يُدع تحقيق أرقام دون قياس. targets: INP <200ms وLCP <2.5s وCLS <0.1، وليست ضمانات.
